# Contract go-route-story: Cards That Explain Themselves

> No Linear ticket exists yet, so no `MPI-NN` code (see `docs/repository-guidance.md`).
> Builds on `docs/contracts/go-route-judge.md` (PR #18, unmerged).

## Context
User feedback on PR #18: (1) the LLM's reasoning and the route diagram do not line up, so it is
hard to see what "this function" or "separate HTTP clients" means; (2) the raw call lists and
"44% overlap" are not immediately understandable and should sit behind a dropdown; (3) a reader
should understand the problem at once, see it in the diagram, and then see the solution.
Decisions given: diagrams are generated by code, never drawn by the LLM; the LLM can annotate
the first diagram where it sees potential issues; a second diagram shows the fix, derived from
the first; keep "maybe intentional" visible; fold cards the model says to leave alone; a caller
and its own callee get a different card type (option A).

The route diagram cannot show the problem because the problem is inside the functions (the same
steps repeated), not in who calls whom. So the new main diagram shows each function's steps, and
the route diagram moves into a dropdown.

## 1. Current state
```
card = pair (first, second) -> sentence "each reach T on separate routes" -> reached-from line
       -> evidence lines (calls, 44%) -> route diagram -> LLM verdict + reasoning (A/B wording)
LLM answer: verdict, summary, differences, counter_argument, citations   (prompt v2)
```

## 2. Target state (+ = new)
```

           per-kind question; answer adds:
             headline        one plain sentence naming both functions and the problem
             action          merge | extract_shared | keep
             steps[]         {name, a_start, a_end, b_start, b_end (0 = absent), same}
             issues[]        {step, function A|B|both, note}      <- annotations on diagram 1
             fix             {summary, shared_name, moved_steps[], stays_in_a[], stays_in_b[]}
             maybe_intentional {reason, would_matter_if}
             (existing: verdict, confidence, explanation, differences, risks, citations)
           code validates: step ranges lie inside the function and do not overlap; issue.step and
           fix step names exist; unknown ones are dropped and counted.
+diagrams.py  pure model (nodes, edges, roles, issue numbers) built by code:
             before(card, steps, issues) -> two step chains, matched steps linked and coloured,
                                            issue markers (1)(2).. on the nodes
             after(before, fix)          -> moved steps of both functions merge into one new node
                                            `shared_name` (dashed), each function keeps its own
                                            steps and points into it  (code transform, not LLM)
             two_routes(card)            -> owner -> helper -> target and owner -> target
             to_mermaid(model), legend(issues)
render.py  card layout:
             title                       "Annotate and Extract"
             PROBLEM   headline (LLM)    fallback without LLM: the existing deterministic sentence
             verdict line                action + verdict + confidence, one line, "advisory"
             DIAGRAM 1 step chains + issue markers; legend "(1) note" below
             FIX       fix.summary + DIAGRAM 2 (after) + "stays in each: ..."
             MAYBE INTENTIONAL (visible)  reason + "matters if ..."
             dropdowns: Evidence (calls, overlap) | Routes and entry points (reached-from, route
                        diagram, routes, sources) | LLM details (explanation, differences, risks,
                        citations verified, steps and source lines table, annotations placed)
           surface: cards with action != keep, ordered merge, extract_shared, unsure, then un-judged;
           folded group "Looked at, probably fine (N)": cards with action keep (compact, expandable)
           no key / judge failed: deterministic layout as today, evidence in a dropdown, no fix
```
Sequence for one pair: card -> prompt v3 (numbered source, names, facts) -> model -> validate
(ranges, names, citations; downgrade rules unchanged) -> diagrams.before -> annotate -> after(fix)
-> render. Judge failure never fails the build (unchanged).

## 3. Definitions
- **two_routes card**: one function reaches the other (`_Reachability.reaches`); owner = the caller.
  Title "`ingestCandidate` reaches `Submit` two ways". Question to the model: are the two routes
  deliberate (success vs failure) or accidental. Verdict enum deliberate | accidental | unsure;
  no steps, no after-diagram.
- **Step diagram fallback**: fewer than 2 valid steps -> deterministic route diagram, no markers.
- **Issue markers**: numbered, max 5, note <= 140 chars, escaped, legend under the diagram. The
  note text is the model's; placement is validated against real step names.
- **After-diagram transform** is a pure function `apply_fix(model, fix)`: merge nodes named in
  `moved_steps` (matched across both functions) into one `shared_name` node.
- **Layout risk**: two parallel chains with cross-links may lay out poorly in Mermaid. Verified by
  rendering locally (below); fallback layout = stacked subgraphs, or a table, decided on evidence.

## Corrections and additions made during implementation

- Legend numbers and notes could drift apart when an issue was skipped for an absent
  side; one accepted-issues list now drives both (found by re-reading `diagrams.py`
  before committing it; its first version had been swept into the preceding red
  commit by `git add`).
- "Stays in each function" is derived from the steps that are not moved. The model
  wrote free text in `stays_in_*`, which the validation dropped (7 names on the first
  real card), so the line came out empty. Only unknown `moved_steps` are now counted
  as dropped fix names.
- The old per-function stays line used `.capitalize()`, which would have lowercased
  step names such as "OpenAI"; replaced.
- The maybe-intentional line doubled punctuation and the words "It would matter if";
  it is now normalised, and a leading common word is lower-cased (names are not).
- Step diagrams run top to bottom (`flowchart TB`): an 11-step chain left to right is
  about 11 boxes wide and GitHub shrinks it. The two-route diagram stays left to right.
  **Not verified visually** (see below).

## Amendment 1: colours, code names, and what red means (after review of PR #19)

Requested after reading the first real run:
- **Red outline = part of the problem**, derived by code: every step the fix moves
  into the shared function, plus any step the model left a note on. It no longer
  depends on which steps the model happened to annotate (it annotated 3 of the 7
  duplicated steps on the first card, because each note covers several steps).
  The numbered notes stay as the model's specific comments.
- **Before and after use the same colours.** Steps that stay keep their original
  colour (orange = the same step in both functions, grey = differs); the new shared
  node is orange with a dashed border (the merged duplicates); nothing is red after
  the fix. A colour key sits under both diagrams.
- **Code names in the boxes.** Each box shows the step name and, on a second line, the
  calls found in that step's source lines (up to 3) and the line range, for example
  `client.Do · L74-78`. Derived from the source at render time, not by the model
  (so cached judgements stay valid); without source access only the line range shows.
- **Click-through.** Hover tooltips are not available in GitHub's Mermaid. Making a
  box a link to its GitHub lines (`click`) is only tried in a temporary experiment on
  the run summary; it is adopted only if the user confirms it renders and works.
  The step table with line links stays in the LLM details either way.
